## 0. THE ONE-PARAGRAPH ANSWER FOR ZERO

You can already **submit** a UserOperation on Base with **no API key** (Candide public, and
`public.pimlico.io`). You cannot get anyone to **pay** for it for free: every one of the 16 live Base
paymasters tested refuses an uninvited account. The only permissionless rail is a **TOKEN paymaster**,
which wants stablecoin up front — currently **0.007078 USDC at 0.01 gwei**, and that number is a
**live quote that scales linearly with `maxFeePerGas`**, not the constant this repo has been treating
it as. Lowering `maxFeePerGas` lowers the entry price. That is the lever.

## 2. THE USEROPERATION STRUCT — v0.6 AND v0.7+ ARE DIFFERENT TYPES

**This is the silent-failure trap the whole lane exists for.** v0.6 has 11 flat fields. v0.7 and later
have **9 fields with three of them bit-packed into `bytes32`**. Encode one with the other's ABI and you
do not get an error that says "wrong version" — you get `execution reverted` with no revert data, which
looks exactly like a paymaster refusing you. I produced that false negative on 10 out of 10 paymasters
before catching it (§7).

### v0.6 — `UserOperation` (11 fields, flat)
```solidity
struct UserOperation {
    address sender;
    uint256 nonce;
    bytes   initCode;               // factory address (20b) ++ factory calldata
    bytes   callData;
    uint256 callGasLimit;
    uint256 verificationGasLimit;
    uint256 preVerificationGas;
    uint256 maxFeePerGas;
    uint256 maxPriorityFeePerGas;
    bytes   paymasterAndData;       // paymaster (20b) ++ data      <- NO gas limits in v0.6
    bytes   signature;
}
```
ABI tuple string:
```
tuple(address,uint256,bytes,bytes,uint256,uint256,uint256,uint256,uint256,bytes,bytes)
```

### v0.7 / v0.8 / v0.9 — `PackedUserOperation` (9 fields, packed)
```solidity
struct PackedUserOperation {
    address sender;
    uint256 nonce;
    bytes   initCode;
    bytes   callData;
    bytes32 accountGasLimits;       // verificationGasLimit (16b) ++ callGasLimit (16b)
    uint256 preVerificationGas;
    bytes32 gasFees;                // maxPriorityFeePerGas (16b) ++ maxFeePerGas (16b)
    bytes   paymasterAndData;       // paymaster (20b) ++ pmVerificationGas (16b) ++ pmPostOpGas (16b) ++ data
    bytes   signature;
}
```
ABI tuple string:
```
tuple(address,uint256,bytes,bytes,bytes32,uint256,bytes32,bytes,bytes)
```

### The packing order — both pairs are (high 16 bytes, low 16 bytes), and they are NOT the same order
Source: https://eips.ethereum.org/EIPS/eip-4337 field table, lines "concatenation of…".

- `accountGasLimits` = **verificationGasLimit** in the high 128 bits, **callGasLimit** in the low 128.
- `gasFees` = **maxPriorityFeePerGas** in the high 128 bits, **maxFeePerGas** in the low 128.

Note the asymmetry: for gas *limits* the verification one is high; for *fees* the priority one is high.
Getting `gasFees` backwards is a nasty one because both values are plausible numbers — nothing reverts,
you just pay a wildly wrong fee. Pack it:
```js
const pack = (hi, lo) => ethers.zeroPadValue(ethers.toBeHex((BigInt(hi) << 128n) | BigInt(lo)), 32);
const accountGasLimits = pack(verificationGasLimit, callGasLimit);
const gasFees          = pack(maxPriorityFeePerGas, maxFeePerGas);
```
Unpack (what you need when reading a real op back out of a `handleOps` calldata):
```js
const h = ethers.toBeHex(v, 32);
const hi = BigInt('0x' + h.slice(2, 34));
const lo = BigInt('0x' + h.slice(34));
```

### `paymasterAndData` also changed shape
- **v0.6:** `paymaster(20) ++ data`. Nothing else.
- **v0.7+:** `paymaster(20) ++ paymasterVerificationGasLimit(16) ++ paymasterPostOpGasLimit(16) ++ data`.
  Minimum length is therefore **52 bytes**. Hand a v0.7 paymaster a bare 20-byte address and it reverts
  with `PaymasterAndDataLengthInvalid()` — see §7, where three live paymasters did exactly that to me.

### JSON-RPC uses a THIRD shape — unpacked, with `factory`/`factoryData`
The struct above is the *on-chain* ABI. When you talk to a **bundler over JSON-RPC** for v0.7+, you send
the **unpacked** form, and `initCode` is split in two:
```jsonc
{
  "sender": "0x…", "nonce": "0x…",
  "factory": "0x…", "factoryData": "0x…",      // v0.7+ RPC: replaces initCode. Omit both if deployed.
  "callData": "0x…",
  "callGasLimit": "0x…", "verificationGasLimit": "0x…", "preVerificationGas": "0x…",
  "maxFeePerGas": "0x…", "maxPriorityFeePerGas": "0x…",
  "paymaster": "0x…", "paymasterVerificationGasLimit": "0x…",
  "paymasterPostOpGasLimit": "0x…", "paymasterData": "0x…",
  "signature": "0x…"
}
```
So there are three representations of the same op — packed on-chain, unpacked over RPC, and v0.6 flat.
**The bundler packs it for you.** Do not send `accountGasLimits` over RPC and do not send
`callGasLimit` to the contract.

### ⚠️ TOPIC INDEX — the mistake that manufactures a fake statistic
`UserOperationEvent` has **three** indexed params, so:
```
topics[0] = event signature
topics[1] = userOpHash
topics[2] = sender          <-- NOT the paymaster
topics[3] = paymaster       <-- THIS one. 0x0 means self-paid.
```
I read `topics[2]` on the first pass and got **"2,812 distinct paymasters, 0 self-paid, 100% sponsored."**
Every part of that was false and none of it looked wrong — it was the *sender* column, which is
naturally almost-all-distinct and never zero. A confident, quantified, fabricated finding, exactly
Trap 2's shape. **The sanity check that catches it: if self-paid is 0.0%, you are reading the wrong
topic.** Real self-paid rates on Base are 10–60% depending on EntryPoint (§5).

## 4. `validationData` — WHAT THE RETURN VALUE MEANS

Both `validateUserOp` and `validatePaymasterUserOp` return a packed `uint256`
(https://eips.ethereum.org/EIPS/eip-4337, "The return value MUST be packed of aggregator/authorizer,
validUntil and validAfter timestamps"):

```
validationData = authorizer (160 bits, low) | validUntil (48 bits) | validAfter (48 bits, high)
```
- `authorizer == 0` → **valid. It would sponsor / accept you.**
- `authorizer == 1` → `SIG_VALIDATION_FAILED`. For a paymaster this means **it wants an operator
  signature you do not have** → VERIFYING type → closed to you.
- any other value → an aggregator/authorizer contract address.
- `validUntil == 0` means infinite. If both `validUntil` and `validAfter` have their **highest bit set**,
  the range is in block numbers, not timestamps.

Test the low bit, not equality with 1 — a time-ranged failure has the timestamps packed above it:
```js
const sigFailed = (BigInt(validationData) & 1n) === 1n;
```

**Crucially, a failing paymaster is specified to RETURN, not revert** ("SHOULD return
SIG_VALIDATION_FAILED (1) without reverting"). So a clean `validationData=1` is a *well-behaved*
refusal, and a **revert is a different animal** — it usually means malformed input, not rejection. §7
turns that into a diagnostic ladder.

## 5. ENUMERATING EVERY BUNDLER AND PAYMASTER ON A CHAIN, FROM LOGS ALONE

No indexer, no API key, no vendor list. The EntryPoint emits one `UserOperationEvent` per op, and that
event names the paymaster. The bundler is just `tx.from` of the enclosing transaction.

```js
// 1. every op, all EntryPoint versions at once (topic0 is version-independent)
const logs = await rpc('eth_getLogs', [{
  address: [EP06, EP07, EP08, EP09],
  topics: ['0x49628fd1471006c1482da88028e9ce4dbb080b815c9b0344d39e5a8e6ec1419f'],
  fromBlock: hex(head - 300), toBlock: hex(head),
}]);

// 2. PAYMASTERS = topics[3]  (topics[2] is the sender — see §3)
for (const l of logs) {
  const paymaster = '0x' + l.topics[3].slice(26);
  if (paymaster !== ZERO_ADDR) count[paymaster]++;

// 3. BUNDLERS = tx.from of the containing transactions (dedupe transactionHash first)
const tx = await rpc('eth_getTransactionByHash', [l.transactionHash]);
const bundler = tx.from;

// 4. version of that bundle = tx.input.slice(0,10):  0x1fad948c v0.6 | 0x765e827f v0.7+
```

### ⚠️ GOTCHAS WHEN SCANNING
1. **`eth_getLogs` is archive-gated on publicnode.** `https://base-rpc.publicnode.com` returns
   `{"error":{"code":-32602,"message":"Archive requests require a personal token…"}}`. This is Trap 2
   verbatim and it fired on me again today. **`https://base.drpc.org` served the same query fine.**
   Read the `error` field before you read `result`.
2. **A wide window silently truncates.** An 800-block query across three EntryPoints returned *exactly*
   2,533 logs for v0.6 and *exactly* 2,533 for v0.7 — an obviously capped number wearing a data
   costume. At 100/200/400 blocks the rate held steady at 3.68 / 3.65 / 3.16 ops per block, i.e. no
   cap. **Run the same query at two window sizes; if the count doesn't roughly scale, you are reading
   a limit, not the chain.** Keep windows ≤300 blocks.
3. **Don't parallelise the follow-up `eth_getTransactionByHash` calls.** Public endpoints rate-limit
   and the failures come back looking like empty results.

## 6. PAYMASTER TYPES — WHICH ONES AN UNINVITED AGENT CAN ACTUALLY USE

| type | how it decides | open to ZERO? |
|---|---|---|
| **VERIFYING** | operator's backend signs the op off-chain; contract does `ecrecover` over `paymasterData` and compares to a stored signer | **NO. Permanently closed.** No amount of on-chain cleverness forges the signature. |
| **TOKEN / ERC-20** | contract checks you hold (and have approved) an accepted ERC-20, then takes payment in `postOp` | **YES — permissionless to anyone holding the token.** This is the whole opening. |
| **DEPOSIT / whitelist** | `mapping(address => bool)` or per-sender balance | No, unless you're already in the mapping |
| **PUBLIC POLICY** (off-chain, ERC-7677) | operator's service applies rules (contract allowlist, spend caps) with no key required | **Maybe** — the only genuinely open question. See §8. |

### How to tell which type a paymaster is, by reading it — no source needed
1. **`eth_getCode`, then look for token machinery in the dispatch table.** A token paymaster must touch
   an ERC-20, so it will reference `transferFrom` `0x23b872dd` / `allowance` `0xdd62ed3e` /
   `balanceOf` `0x70a08231`, and usually exposes a token config getter. A verifying paymaster's
   bytecode is mostly hashing + `ecrecover` and has no ERC-20 surface.
2. **Look for a public signer getter.** `verifyingSigner()` `0x23d9ac9b`, `signer()`, `owner()` present
   ⇒ almost certainly VERIFYING.
3. **`entryPoint()` `0xb0d691fe`** tells you which EntryPoint version it serves, so you build the right
   struct. Do this FIRST — §7 explains what happens if you don't.
4. **The decisive test is the admission call in §7.** Bytecode heuristics are Trap 4 (regexes lie in
   both directions); an `eth_call` cannot.

## 7. THE ADMISSION TEST — CALL `validatePaymasterUserOp` AS THE ENTRYPOINT

This is the only test that answers "would this paymaster pay for *me*". It's free, unlimited, and works
on unverified contracts. Every paymaster restricts `msg.sender` to the EntryPoint, so you **spoof `from`**
— which `eth_call` lets you do for free, because nothing is signed.

```js
const I = new ethers.Interface([
  // v0.7+ shape. For v0.6 swap in the 11-field tuple and selector 0xf465c77e.
  'function validatePaymasterUserOp(' +
  'tuple(address sender,uint256 nonce,bytes initCode,bytes callData,bytes32 accountGasLimits,' +
```

### ⚠️ THE FALSE-NEGATIVE THAT ALMOST GOT WRITTEN DOWN
My first pass ran the admission test against all 10 targets using the **v0.7 struct and the v0.7
EntryPoint as `from`**, uniformly. Result: **10/10 `execution reverted`** — a tidy, plausible,

Then a second failure stacked on top: several calls came back `over rate limit` from the RPC and my
code classified them as reverts, i.e. as refusals. **A transport error is not a contract answer.**

The fixes, in order of importance:
1. **Bind each paymaster to its own EntryPoint version first** (from the log scan, or `entryPoint()`),
   and build the matching struct.
2. **Classify transport vs revert.** Match `/rate limit|too many|timeout|archive|429|502|503/i` on the
   error message and *retry on another provider* — never fold it into the result.
3. **Emit a third verdict, `UNKNOWN`.** Open / closed / unknown. If the call never succeeded you have
   no reading, and "no reading" must never silently become "closed". Counting unknowns as refusals is
   how a fixable wall gets recorded as physics.
4. Space the calls (~350ms) and go sequential.

`PaymasterAndDataLengthInvalid()` = **`0xcc32193e`** (confirmed by keccak match). Three paymasters
returned it. It means your `paymasterAndData` was under 52 bytes — **your bug, not their policy.** Fix
it and re-test before recording that paymaster as closed.

## 10. ERC-7677 — `pm_getPaymasterStubData` / `pm_getPaymasterData`

Spec: https://eips.ethereum.org/EIPS/eip-7677 (status: **Review**, not Final — implementations vary).
Both methods take the same 4 positional params: `[userOp, entryPoint, chainId, context]`.
The `userOp` **carries no `signature`** — the user signs after these fields are filled in.

```jsonc
// pm_getPaymasterStubData -> stub values for gas estimation
["…userOp without signature…", "0x0000000071727De22E5E9d8BAf0edAc6f37da032", "0x2105", { "token": "0x8335…2913" }]

// returns, EntryPoint v0.7+:
{ "paymaster": "0x…", "paymasterData": "0x…",
  "paymasterVerificationGasLimit": "0x…",   // MAY be returned
  "paymasterPostOpGasLimit": "0x…",         // MUST be returned for v0.7 — the paymaster pays it,
                                            // so it will not trust your estimate
  "sponsor": { "name": "…", "icon": "…" },  // optional
  "isFinal": true }                         // if true, SKIP pm_getPaymasterData entirely

// returns, EntryPoint v0.6:  { "paymasterAndData": "0x…" }
```
`pm_getPaymasterData` returns the same minus the gas limits and `isFinal` — the real, non-stub values.

**Version branching is the service's job, not yours:** "Paymaster services MUST detect which entrypoint
version the account is using and return the correct fields." So a v0.6 request gets `paymasterAndData`
and a v0.7 request gets split `paymaster`/`paymasterData`. If you get the wrong shape back, you sent the
wrong `entryPoint`.

**`isFinal: true` saves a round trip** — it's set when `paymasterData` contains no signature, which is
typical of token paymasters. Check for it.

`context` is provider-defined. Candide's keys (from its docs):
- `token` — ERC-20 address, to pay gas in that token
- `sponsorshipPolicyId` — private policy (needs a dashboard account ⇒ **dead end for ZERO**)
- `signingPhase: "commit" | "finalize"` — v0.9 only, two-phase parallel signing
Pimlico requires `sponsorshipPolicyId` on its public host and **403s without one**.

Also on Candide: `pm_sponsorUserOperation` (older, non-7677) takes `[userOp, entryPoint, context]` —
note **3 params, no chainId** — and returns the paymaster fields *plus* gas overrides when a gas policy
is used. Under a gas policy it returns mandatory `callGasLimit`, `verificationGasLimit`,
`preVerificationGas`, `maxFeePerGas`, `maxPriorityFeePerGas`; under ERC-20 payment it returns **no**
gas overrides. Different return shape depending on payment mode — don't assume the fields are there.

## 11. THE PUBLIC-GAS-POLICY QUESTION — STILL OPEN, AND THE REFUSALS ARE A STAGED LADDER

Candide distinguishes **public** gas policies (third-party funded, *no policy id required*) from
**private** ones (need a dashboard key). If a public policy ever matches ZERO's op, that is free gas
with no token and no signature. This is the open frontier and it is **not** closed.

**Measured today** — `pm_sponsorUserOperation` with empty context `{}`, no key:

| what I sent | refusal |
|---|---|
| synthetic op, undeployed sender, `callData: "0x"` | `sponsored-validator: callData reverts` |
| synthetic op, junk callData | `sponsored-validator: callData reverts` |
| **real op replayed from a live bundle, original (spent) nonce** | `sponsored-validator: callData reverts` |
| **real op, sender's CURRENT nonce from `getNonce()`** | **`this user operation does not qualify for any publicly available gas policy`** |

### That last row is the whole lesson
The refusal **changes when the op becomes simulable**. The validator runs in stages:

```
stage 1  simulate the op        -> fails: "callData reverts"        <- says NOTHING about policy
stage 2  match against policies -> fails: "does not qualify for any publicly available gas policy"
```
Three real user operations that had **genuinely executed on-chain minutes earlier** were rejected with
`callData reverts` purely because their nonces had advanced by 1. **A stale nonce masquerades as a
policy rejection.** Anyone probing this with a synthetic or replayed op will conclude "no public
policies exist" and be wrong about *why*.

**Correct probe procedure:** deployed sender · fresh nonce from `getNonce(sender, key)` (`0x35567e1a`,
key = `nonce >> 64`) · callData that actually executes. Only a stage-2 message is evidence about policy.

**And stage 2 is a TECHNICAL wall, not an AUTH wall** — the exact distinction `gas_sources` encodes.
It says *"you don't match one"*, not *"give me a key"*. Public policies exist; we haven't matched one.
The variables to sweep: **target contract** (policies are usually allowlisted to a sponsor's own dapp),
op size, sender's account type. Passing a bogus `sponsorshipPolicyId: "1234"` did **not** produce an
auth error either — it fell through to the same stage-1 message, i.e. the id is validated after
simulation.

**Do not record this as closed.** Record it as: *stage 2 reached, no public policy matched for the
contracts we've tried.*

## 12. GOTCHA INDEX — read before spending anything

1. **v0.6 and v0.7 UserOperations are different ABI types.** Mismatched encoding gives a bare
   `execution reverted` that is indistinguishable from rejection. Bind paymaster → EntryPoint first.
2. **`topics[3]` is the paymaster, `topics[2]` is the sender.** Reading `[2]` yields "100% sponsored",
   which is fabricated. If self-paid comes out 0.0%, you have the wrong index.
3. **`gasFees` = priority(high) | maxFee(low); `accountGasLimits` = verification(high) | call(low).**
   Different orders. Reversing `gasFees` reverts nothing and costs money.
4. **`paymasterAndData` must be ≥52 bytes on v0.7+.** Under that: `PaymasterAndDataLengthInvalid()`
   `0xcc32193e`. Your bug, not their policy.
5. **`eth_getLogs` is archive-gated on `base-rpc.publicnode.com`.** Check the `error` field; fail over
   to `base.drpc.org`.
6. **Wide log windows silently truncate.** Two identical counts across two EntryPoints = a cap. Probe
   the same window at two sizes and confirm the rate scales. Stay ≤300 blocks.
7. **RPC `over rate limit` is not a contract revert.** Classify transport separately and emit
   `UNKNOWN`. Never let "couldn't measure" become "refused".
8. **Candide's required-allowance is linear in `maxFeePerGas`, not a constant.** 0.007078 USDC at
   0.01 gwei today vs the 0.009087 in `CLAUDE.md`. Re-quote every time; lower the fee to lower the price.
9. **Its allowance error has two wordings ("allowance lower" / "balance lower") for one condition.**
   Parse the hex, ignore the prose. You need balance *and* approval.
10. **A paymaster that fails validation RETURNS `validationData=1`; it does not revert.** A revert
    means malformed input far more often than rejection.
11. **`AA23` = your account failed. `AA33` = the paymaster failed.** One character, opposite meanings.
12. **`pm_getPaymasterStubData` is not free of the token balance check** on Candide, despite ERC-7677's
    framing. You can't estimate before you're funded.
13. **`eth_getUserOperationReceipt` returns `null`, not an error, while pending.** Poll; don't retry as
    if failed.
14. **Bundler `eth_supportedEntryPoints` returns checksummed, paymaster returns lowercase** (Candide).
    Lowercase both before comparing.
15. **A replayed userOp always fails simulation** — its nonce is spent. Refetch `getNonce` first, or
    every probe reads as a policy refusal.
16. **`public.pimlico.io` ≠ `api.pimlico.io`.** The former is keyless for bundler methods; the latter
    401s. Collapsing them loses a working rail on 7 chains.
17. **Pimlico public 429s after ~2 rapid calls.** Real but thin. Don't scan with it.
18. **EntryPoint v0.9 exists and is live.** Don't assume v0.7 is current.
19. **Doc example addresses are filler.** `0x7e3393eb…` in Candide's docs is not a real Base paymaster.
    Take addresses from live API responses or the chain.
20. **The EntryPoint address is the same on every chain.** Don't hunt for per-chain variants.
